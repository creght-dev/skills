# Creght Internationalization (i18n)

Creght multilingual is **field-level**: one content item holds every language,
translations live inline, and `talizen/cms` decodes them by the current locale on read.
There is no "one item per language" and no translation-group key to manage — the
item *is* the group. This mirrors how Wix / Framer / Webflow work.

## 1. Enable it

Add `i18n` to `talizen.config.ts`:

```ts
export default {
  i18n: {
    defaultLocale: "en",
    locales: ["en", "zh", "ja"],
    localeDetection: true, // default true; redirect unprefixed visits by cookie/Accept-Language
  },
}
```

Users can configure this from the editor's **Settings → Languages** panel; you may
also edit `talizen.config.ts` directly.

## 2. Routing

- Default locale has **no** prefix: `/about`. Other locales are prefixed:
  `/zh/about`. `/{anyConfiguredLocale}/...` is also valid (e.g. `/en/about`), which
  is handy for language switchers.
- Page resolution: the platform first looks for a locale-specific file
  (`/page/zh/About.tsx` or `/page/[lang]/About.tsx`), then falls back to the shared
  file (`/page/About.tsx`). So you can keep one shared page for all locales, or
  override a single locale with its own file — mix freely. `index` maps to its
  folder root (`/page/zh/Index.tsx` -> `/zh`).
- Prefer **shared pages + `context.locale`** for content-driven sites; reserve
  per-locale files for pages whose layout genuinely differs by market.
- `[lang]/Index.tsx` (a root catch-all) is discouraged with the default-no-prefix
  strategy because `/:lang` greedily matches any top-level path; use static `zh/`
  folders or shared pages at the root.

### Links and language switcher

Use talizen's locale-aware `<Link>` (v0.2.0+) for internal links — it auto-prefixes
the current locale, so you never thread `locale` through props. Never use a router
library.

```tsx
import { Link, useLocale } from "talizen"

// Internal link — stays in the current language (on /zh it renders /zh/blog/hello):
<Link href="/blog/hello">Read</Link>

// Language switcher — pass `locale` to switch (also remembers via CREGHT_LOCALE cookie):
function LangSwitcher() {
  const { locales } = useLocale()
  return (
    <nav>
      {locales.map((l) => (
        <Link href="/" locale={l}>{l}</Link>
      ))}
    </nav>
  )
}
```

For a raw string URL (e.g. an `<img>` or a non-`<Link>` case) use
`localizedPath("/blog", locale?)` from `talizen`. A plain `<a href="/blog">` does **not**
add the prefix and will drop the visitor out of the current language — prefer `<Link>`.

### The `CREGHT_LOCALE` cookie (explicit choice)

Detection order for an unprefixed path is: `CREGHT_LOCALE` cookie → `Accept-Language`
→ default locale. The cookie is the **explicit override** and takes priority over the
browser language.

- Passively viewing a prefixed page (e.g. `/zh`) does **not** set the cookie — only a
  deliberate language choice should. So detection normally follows the visitor's
  browser language.
- To persist a manual choice (e.g. an English-browser user who picks 日本語), the
  language switcher may set the cookie on click:
  `document.cookie = "CREGHT_LOCALE=ja; path=/; max-age=31536000"`. After that, `/`
  redirects that visitor to `/ja` until they choose otherwise. Clearing the cookie
  reverts to browser-language detection.

## 3. Reading the locale in a page

Use the accessor that matches where you are (this mirrors next-intl's `getLocale`
server function vs the `useLocale` component hook):

- **Server-side** — `getServerSideProps` / `generateMetadata` (data fetching, **not**
  component render): prefer `getLocale()` from `talizen` (v0.2.3+) over `context.locale` —
  same value, one accessor that needs no `context` threading. `context.locale` /
  `context.locales` / `context.defaultLocale` also work when you already hold `context`.
  Do **not** call the `useLocale()` hook here — it is for component render only.

  ```tsx
  import { getLocale } from "talizen"

  export async function getServerSideProps(context) {
    const { locale } = getLocale()          // === context.locale
    const { list } = await listContents("blogs", { limit: 10 }) // decoded to `locale`
    return { props: { list } }
  }
  ```

- **In a component** (client render) — **always** use the `useLocale()` hook (v0.2.0+);
  it needs no prop-threading:

  ```tsx
  import { useLocale } from "talizen"

  function Hero() {
    const { locale, locales, defaultLocale } = useLocale() // "en" | "zh" | "ja"
    return <h1>{locale === "ja" ? "ようこそ" : "Welcome"}</h1>
  }
  ```

> ⚠️ **Never detect the locale by hand.** Don't parse the request URL
> (`url.startsWith("/ja/")`) or query params — the router strips the locale prefix, so URL
> checks silently fail. Always use `getLocale()` / `context.locale` / `useLocale()`, and
> fall back to `context.defaultLocale`, never a hardcoded literal like `zh`.

CMS data read via `talizen/cms` arrives already decoded to the current locale (see §4 —
just read the fields, as in the `getServerSideProps` example above). You usually do
**not** branch templates on locale for CMS content — the values arrive already
localized. Branch only for locale-specific static copy or layout.

### UI text with `useTranslations()` / `getTranslations()`

CMS content is localized via `_i18n` (§4) — page code just reads the fields. For **UI
chrome** (buttons, nav, labels — strings written in code, not in the CMS), use message
catalogs + `useTranslations()` (v0.2.1+):

1. One JSON per locale under `/messages` in the project (translator-friendly; only the
   current locale is loaded at runtime):

   ```jsonc
   // /messages/en.json
   { "home": { "title": "Welcome", "greeting": "Hi {name}" } }
   // /messages/zh.json
   { "home": { "title": "欢迎" } }   // missing keys fall back to the default locale
   ```

   Keep the default locale's file complete — it is the fallback base.

2. Read it in a component with `useTranslations()` (no prop-threading), or in
   `getServerSideProps` / `generateMetadata` with `getTranslations()` (v0.2.3+, the
   non-hook form):

   ```tsx
   import { useTranslations } from "talizen"

   function Hero() {
     const t = useTranslations("home")   // namespace optional
     return <h1>{t("title")}</h1>        // zh -> "欢迎"; a missing key -> default locale
   }

   // server-side (get* form, not a hook):
   import { getTranslations } from "talizen"
   export function generateMetadata() {
     const t = getTranslations("seo")
     return { title: t("home_title") }
   }
   ```

   `t("greeting", { name })` interpolates `{name}`; `t("missing")` returns the key.
   Without a namespace, use full paths: `t("home.title")`.

The platform reads `/messages/{locale}.json` (merged over the default locale for per-key
fallback) and injects it for both SSR and the browser, so `useTranslations` returns the
same text on server and client. Do **not** hand-roll a big in-code dictionary keyed by
locale — use `/messages` + `useTranslations` for UI text, and `_i18n` for CMS content.

## 4. Content storage: the `_i18n` convention

Each content item stores the default language in the fields themselves; other
languages go under a reserved `_i18n` key, grouped by locale, holding **only the
translated fields**:

```jsonc
{
  "title": "Hello",             // default language, unchanged
  "cover": "a.png",             // no override -> shared across locales
  "published": true,            // no override -> shared
  "_i18n": {
    "zh": { "title": "你好" },   // only translated fields
    "ja": { "title": "こんにちは" }
  }
}
```

Decode rule: on read, `talizen/cms` (`listContents` / `getContent` /
`getContentWithPrevNext`, v0.2.3+) returns each item already merged for the current
locale — `_i18n[locale]` overlaid on the base fields, any missing field falling back to
the default language. Content **without** `_i18n` is returned unchanged — no migration.

## 5. Which fields translate (`localizable`)

Mark translatable fields in the collection schema (Settings → the collection's
field editor → "Translatable"). Guidance by field type:

| Field | Translate? |
| --- | --- |
| text / rich text / title / description / SEO | Yes |
| image / media | Usually (only if it differs per language/market) |
| slug | Optional (localized URLs); keep a stable id for relations — see §7 |
| boolean / checkbox, number / date | No — shared |
| enum / select | Value: No (stable key). Label: yes, via labels — see §6 |
| relation / reference | No — points to one item that resolves per locale |

Untranslated `localizable` fields fall back to the default language.

## 6. Enum / select labels

The enum **value** is a stable machine key (e.g. `news`) and is never translated —
translating it would break filtering, counting, and logic across locales. Only the
**display label** is localized, stored on the field schema:

```jsonc
{
  "type": "string",
  "enum": ["news", "tutorial"],
  "enumLabels": { "news": "News", "tutorial": "Tutorial" },      // default language
  "enumLabelsI18n": { "zh": { "news": "新闻", "tutorial": "教程" } } // per-locale
}
```

Set these in the schema field editor's enum options (per-locale label inputs appear
once the site has `locales` configured). For fixed, code-owned option sets this
label table is the right tool. If an "enum" is really an editorial, growing taxonomy
that needs its own pages (categories, tags), model it as a **relation to a
collection** instead and localize those entries like any content.

## 7. Slugs and relations — anchor on stable ids, never slugs

- A localized slug (`/zh/ni-hao`) is fine for SEO, but **relations and
  cross-references must target a stable identity** (the item's id), not a slug.
  Slugs are output (URLs), get edited, and differ per locale — anchoring on them
  breaks links.
- To link a blog to its author, store the author's stable id/key and resolve the
  author for the current locale at render time (the author item carries all
  languages). Do not store a locale-specific author slug.

## 8. AI translation workflow

When asked to make a site (or a collection) multilingual, do this — and only touch
what's needed:

1. **Config**: add `i18n` (defaultLocale + locales) to `talizen.config.ts`.
2. **Schema**: mark human-facing text/media fields `localizable`; add
   `enumLabelsI18n` for any enum labels. Create new collections with `create_collection` if the environment
   exposes it, otherwise via the schema editor. Never mark enum values, booleans, numbers, or relations localizable.
3. **Pages**: keep pages shared and read `context.locale` where locale-specific
   static copy is needed; add a language switcher with plain anchors. Do not
   duplicate whole pages per locale unless layout truly differs.
4. **Content translations**: put translated values under the item body's
   `_i18n[locale]`, translating **only** `localizable` fields, leaving base
   (default-language) fields and non-localizable fields untouched. Keep enum values
   as their stable keys. Content is normally entered/edited through the CMS UI; when
   you produce translations, follow exactly this shape so `talizen/cms` decodes
   them on read.

Because identity is the single item, you never build or display a "translation
group" and never write per-locale duplicate items — that fragility (Strapi/Prismic
"document-level") does not exist here.

## Do / Don't

- DO store enum values as stable keys; localize labels via `enumLabelsI18n`.
- DO put translations under `_i18n[locale]`, only for `localizable` fields.
- DO read the locale via `getLocale()` (server) / `useLocale()` (component); let CMS
  values arrive already localized.
- DON'T manually parse the request URL or query params to detect the locale — the router
  strips the locale prefix, and a hardcoded fallback desyncs from `defaultLocale`.
- DON'T translate enum values, booleans, numbers, ids, or relation targets.
- DON'T anchor relations/links on localized slugs.
- DON'T create one content item per language, or a `groupKey`.
- DON'T use a router library, or a plain `<a>` for internal links on a localized site
  (it drops the locale prefix) — use talizen's `<Link>` / `localizedPath()`.
